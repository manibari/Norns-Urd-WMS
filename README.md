# Urd-WMS

**輕量包材批次管理 —— 拍箱子取代抄表單，FIFO 稽核、追溯、提醒。**

不需要買一整套 ERP，就能回答「哪一批包材、什麼時候、被誰、用在哪個產品上」。

## 定位

Norns 產品線 **Urd（記錄）** 層。前身是 Norns-ERP 的 M7 模組，2026-08-21 抽出成獨立可配置產品。

| 項目 | 內容 |
|------|------|
| 核心價值 | **紀錄** —— FIFO 擋單是疊在紀錄之上的提醒，不是主角 |
| 首發客戶 | 金軒揚食品（美珍香）成品包裝區 —— 取代紙本表單 P-4-P-01-07 |
| 資料 SoT | 自持批次庫存（`inventory_lot`），不依賴外部 ERP |
| 可配置 | Day 1 設定驅動：表單欄位 / 機台清單 / 正規化對映 / 提醒門檻 / 報表格式。**每廠一套部署**（非 SaaS 多租戶） |
| 明確不做 | 會計分錄、儲位/揀貨/盤點、成品出貨、與 Norns-ERP 同步（M7 各走各的） |

## 權限層級 ≠ 職位

**職位**（倉管／廠長／品管／作業員）是給人看的職稱，填在每個人身上；
**權限層級**是伺服器檢查的三層。倉管和廠長是不同的職位，但需要系統做的事一樣，
所以都是 `manager` —— 混在一起的話，每多一個職稱就要多一組權限，存取模型很快就爛掉。

| | user | manager | admin |
|---|:--:|:--:|:--:|
| 領用登錄、補明細 | ✅ | ✅ | ✅ |
| 收貨建批、維護型號 | | ✅ | ✅ |
| 覆核放行非 FIFO | | ✅ | ✅ |
| 看系統日誌 | | ✅ | ✅ |
| 批次修正與刪除 | | | ✅ |
| 選項、人員與角色 | | | ✅ |

「一般作業員無覆核權限」是 requirement US-4 的明文要求。三層的**顯示名稱**可以改成你們的叫法，
權限不會跟著變 —— 那是系統設計，不是稱呼。

**權限在伺服器端把關**，每個端點各自檢查；前端隱藏選單只是方便，因為藏起來的選單離「直接打網址」只有一步。
403 訊息會說明需要哪個角色 —— 只說「沒有權限」每次都會變成一通電話。

**簽核用登入身分**：收貨單的「記錄人」寫的是登入者，不是下拉選的名字。雙簽是這張單的控制點，
選單式簽名等於誰都能簽別人的名字。管理者建的帳號第一次登入會被強制改密碼，否則管理者永遠知道別人的密碼。

密碼用 PBKDF2-SHA256 + per-user salt，只要求長度 ≥ 8：大小寫符號那套規定只會逼出 `Password1!` 和便利貼。

## 每箱數量的單位跟著品項走

膜是米、鋁袋是張、脫氧劑是包 —— 一個全域單位對多數列都是錯的，所以單位存在品項上
（`pack_unit`），換算提示與庫存顯示都帶各自的單位。

**效期也是品項的性質**：驗收單註記寫明「肉乾真空膜不需填有效日期」。品項標記為「有效期」後，
收貨就**必須填有效期限**，沒填會被擋下來。

不做「製造日＋保存天數」推算 —— 推算出來的是一個沒人寫下、也沒人能拿去跟箱子核對的日期，
而驗收單本來就有「有效日期」欄，答案應該從那裡來。

## 影像來源可以是網路相機

領用的「影像辨識」不在乎照片從哪來 —— 手機拍、上傳檔案、或**系統設定裡接一台 TCP/IP 相機**，
之後的辨識、批次比對、FIFO 判定完全同一條路。這就是 M7 架構把擷取層抽開的用處：
加一台固定相機是「多一個來源」，不是「再寫一套領用流程」。

兩種傳輸都是純 TCP，且只用標準庫（產線上不該為了拍張照去連套件庫）：

- **HTTP snapshot** — 抓 `http://ip:port/path`，幾乎所有 IP 相機都有，支援 basic auth
- **原始 TCP** — 開 socket、可選送出觸發字串、讀到 JPEG 結束標記為止

測試連線會說清楚失敗在哪 —— 連不到、逾時、或「回傳的不是 JPEG，開頭是 `<html>401…`」。
最後那個是最常見的：路徑打錯拿到登入頁，而「失敗」兩個字會讓人跑去查網路。

## 辨識速度是量出來的，不是猜的

| 模型 | 中位耗時 | 型號＋兩個日期 |
|---|---:|---|
| `gemini-3.7-flash`（預設） | **8.4s** | 3/3 全對 |
| `gemini-pro-latest` | 19.1s | 3/3 全對 |
| `gemini-3.5-flash` | 11.8s | ✗ 進貨日讀錯 |

⚠️ **單次計時會騙人**：pro 第一次跑出 6.9 秒，看起來比 flash 還快，中位其實是 19.1 秒。

## FIFO：指引只指一批，判定仍然寬鬆

排序看的是**製造日**，不是進貨日 —— 要控管的是庫齡，而供應商壓貨或延遲交貨會把到貨順序
打亂（三月製八月到的膜，比七月製六月到的更舊）。同製造日的多批**都合法**（requirement
US-3），但畫面上只有一批掛「FIFO 應領」—— 兩批都標「應領」等於什麼都沒說；其餘同製造日的
標「同製造日．可領」，領了不會被擋。

沒填製造日的批次排**最後**（未知年齡不得插隊）。整個料號都沒填時退回進貨日排序，
API 用 `fifo_basis` 說明目前依據哪一欄，畫面照實講「暫時改用進貨日」。

## 檢驗項目是二選一，不是打勾

外觀、顏色、規格尺寸都用「正常／不正常」而不是 checkbox —— **沒勾的 checkbox 分不出
「不正常」和「還沒檢查」**，那是驗收紀錄上完全不同的兩件事。

選了「不正常」就**必須寫哪裡不正常**：記了有問題卻沒記是什麼問題，召回時那筆紀錄幫不上忙。
若有項目異常但判定仍是合格，畫面會提醒確認 —— 這樣寫是可以的（有些瑕疵不影響使用），
但要是刻意的。

## 批次有三種狀態

`qty_received`（收了幾箱，不變）和 `qty_on_hand`（剩幾箱，遞減）都留著，才分得出：

- **未動用** — 收進來還沒領過
- **領貨中** — 領了一部分（顯示 已領/收進）
- **已領完** — 剩 0，整列反白但不刪除（它是歷史）

只看剩餘量分不出來：剩 3 箱可能是收 3 箱沒動，也可能是收 10 箱領了 7。

## 誰的順序存在哪

| | 存哪 | 為什麼 |
|---|---|---|
| 品項主檔的**列順序**（拖把手） | 伺服器 | 主檔怎麼分組（膜歸膜、天天用的放最上面）是對資料的決定，大家看到的該一樣 |
| **欄位順序 / 欄寬**（拖標題 / 拖邊界） | 瀏覽器 localStorage | 那是個人閱讀習慣，維護主檔的人和查庫存的人在意的欄位本來就不同 |

品項主檔按自訂順序，庫存總覽按最近進貨 —— 同一支 API 用 `?order=` 分開，
而不是各畫面自己排（那會讓兩邊對「第一個」的定義悄悄不一致）。

## 什麼可以改、什麼不能刪

| 資料 | 可否修改 | 可否刪除 |
|---|---|---|
| **批次**（收貨登錄） | ✅ 可改，變更前後值寫入異動軌跡（US-1 要求「不可靜默改」） | ⚠️ **只在沒有任何領用紀錄時**。有領用就拒絕——刪掉會讓那些紀錄指向不存在的批次，追溯當場斷掉。要退出流通請把數量改成 0 |
| **領用紀錄**（含被擋下的） | ❌ | ❌ 永久保存。這是交付物本身（requirement §2.1） |
| **字典項目** | ✅ 可改名 | ⚠️ 只能停用不能刪，舊紀錄指向它 |

## 所有下拉都吃字典

收貨與領用畫面沒有一個選單是寫死的。分兩種來源：

- **品項的屬性**（原物料名稱／規格）→ 讀品項表的 distinct 值。它們只描述那一個品項，
  另開字典等於同一件事存兩份。要改就編輯那個品項。
- **獨立實體**（廠商／職位／機台／產品名稱／覆核原因）→ `dictionary` 表，可新增／改名／停用／刪除。
  廠商在這裡是因為一個廠商供應多個品項，它不是某個品項的欄位。

停用與刪除是兩件事：停用只是不出現在選單、隨時可復原；刪除是整個移除。
兩者都不影響既有紀錄 —— 紀錄存的是當時選的文字，不是參照。

停用而非刪除：舊紀錄指向這些值，刪掉會讓追溯報表出現空白，比顯示一個已淘汰的名字更糟。
現場在收貨表單當場新增的值也會寫回字典，不會只留在畫面上。

## 型號 vs 料號（識別方式，容易搞混先講）

| | 例 | 誰在用 | 用途 |
|---|---|---|---|
| **型號** | `T6050BSW` | 倉管寫在驗收單上 | **主識別**、米數對照表的 key |
| 箱上完整料號 | `2003.T7320BC-340X900-P1` | 沒有人手打 | 影像辨識讀到的字串，用來對回型號 |

驗收單只有型號，箱上標籤只有完整料號。系統兩邊都存，領用拍照時會交叉檢查——
標籤讀到的料號跟所選型號對不起來，當場跳警告（選錯型號或拿錯箱）。

## 跑起來

```bash
echo 'GEMINI_API_KEY=...' > .env          # 辨識用；沒有的話流程仍可跑，會退人工挑批次

# 後端 :8071
python3 backend/seed.py
set -a && . ./.env && set +a
python3 -m uvicorn app.main:app --app-dir backend --port 8071 --reload

# 前端 :3071
cd frontend && pnpm install && pnpm dev
```

開 http://localhost:3071 ，先登入。首頁是**庫存總覽**：各品項在庫、批次數，以及最重要的
「下一個該領哪批」—— 知道有 9 箱沒有用，還得知道下一箱是哪一箱。

seed 帳號：

| 帳號 | 顯示名 | 職位 | 權限層級 | 密碼 |
|---|---|---|---|---|
| `peter` | Peter | 資訊 | admin | `peter0821` |
| `kuo` | 郭 | 倉管 | manager | `urdwms2026` |
| `huang` | 黃揚文 | 廠長 | manager | `urdwms2026` |
| `operator` | 線上作業員 | 包裝線作業員 | user | `urdwms2026` |

畫面依流程排：
**1. 基本資料 → 2. 收貨建批 → 3. 領用登錄 → 4. 紀錄與追溯**，外加「提醒」。

基本資料排第一是因為它在流程第一，不是因為它是「設定」——沒有型號就沒東西可收，
沒有機台和產品就沒辦法記領用。

沒有前置資料時 UI 會往上游導 —— 選到沒在庫批次的料號，領用畫面不會給你一個按了沒用的表單，
而是說明「FIFO 要排序就得知道還有哪幾批在庫」並給收貨入口。

## 狀態

**垂直切片 demo 可跑**（US-1/2/3/4/5 核心路徑 + US-6/8 提醒）。範圍見下表。

| | 已做 | 未做 |
|---|---|---|
| 收貨 | **兩步**：進貨資料（品項／廠商／日期／數量）→ 檢驗項目（逐項編號往下：規格尺寸／製造日期／有效期限／外觀／顏色／判定）＋雙簽 | 採購單、供應商主檔 |
| 領用 | **三步**：選品項（手動／影像辨識二選一）→ 選批次（依製造日排序）→ 數量（預設 1）；FIFO 應領預選、硬擋、同 transaction 扣帳 | 離線暫存、連拍擇優 |
| 稽核 | 覆核放行（必填原因）、**異動軌跡畫面**（含變更前後值）、影像永久留存 | RBAC（目前單一 demo 身分，管理功能沒有真的權限把關） |
| 提醒 | 效期（優先用標示的有效日期）／呆滯／低水位／明細待補／**驗收不合格待處理** | 稽核異常告警（US-9） |
| 追溯 | 紀錄列表 + 影像 drill-down | 正反向查詢頁、報表匯出 |
| 基本資料 | 型號與米數對照表 ＋ 七類字典（廠商／原物料名稱／規格／人員／機台／包裝產品／覆核原因），**所有下拉都從這裡來** | 欄位定義本身仍寫死（US-11 只做了選項層） |

辨識 PoC 初步結果（n=2 有章樣本，`gemini-pro-latest`）：命中 100%、誤命中 0%、
兩張陷阱樣本正確回 null。**撐不起結論**，真 PoC 仍需現場實拍 100–200 張分層樣本。
