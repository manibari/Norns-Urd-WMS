# M7 包材領用 FIFO 稽核 — 系統架構

> 2026-08-21｜對應 requirement `docs/requirements/packaging-material-usage-fifo.md`
> 實作順序見 `task_plan.md` Phase 1-5。圖檔：`m7-architecture.mmd` / `m7-flow.mmd`

## 一句話

**把「哪一批包材、什麼時候、被誰、用在哪個產品上」變成一份查得到、追得到、稽核得了的紀錄**
——取代紙本表單 P-4-P-01-07。FIFO 硬擋是疊在紀錄之上的提醒。

## ★ 優先序：紀錄 > 擋單（2026-08-21 拍板）

交付的核心是**紀錄**，不是攔截。擋單是有價值的加值，但它服務於紀錄，不能反過來威脅紀錄。

| 原則 | 具體含意 |
|---|---|
| **被擋 ≠ 沒發生** | `blocked_fifo` 是一筆**完整紀錄**（誰／何時／哪台機／拿了哪批／應該拿哪批／當時影像），永久保存、不可刪。不是「操作失敗」 |
| **畫面語氣** | 紅屏不是「失敗，請重試」，是「**已記錄，請換一箱**」。前者誘發「再拍一次讓它過」，後者讓人知道重拍沒用 |
| **降低繞過動機** | 現場清楚「反正都會被記下來」→ 繞系統只會多一筆難看的紀錄，不會消失。這是對「硬擋逼人繞系統」最有效的解 |
| **取捨時選記** | 若要在「擋不擋得住」與「記不記得下來」之間選，**選記**。擋失敗只漏一次違規；沒紀錄是核心價值破洞 |
| **測試優先序** | 最高優先不是「違規被擋」，是「**任何情況下都留得下紀錄**」：斷網、拍到一半離開、重複拍、系統當掉重開、覆核駁回 |

## 2. 核心設計：辨識是「認出是哪一批」，不是「取得進貨日」

![判定流程](m7-flow.png)

這是整個架構最重要的一個判斷，值得單獨講。

**進貨日不是從照片來的。** 它在**收貨**時就由倉管登錄進 `inventory_lot` 了
（來源是箱上的驗收章，但那是收貨當下讀的，不是領用當下）。

所以領用時的辨識，任務是**認出工人手上這箱對應系統裡的哪一個批次**——
從一份**已經存在、而且很小**的候選清單裡挑一個，不是開放式地讀出一個值。

```
辨識讀出日期 → 比對「該料號 qty_on_hand > 0 的批次清單」（通常 1-5 批）
  ├─ 命中唯一 → 鎖定批次 → 跑 FIFO 判定
  ├─ 對不上任何一批 → 辨識錯 or 此箱未入帳 → 退人工
  └─ 命中多個 → 退人工確認
```

### 為什麼這個設計重要

**它讓「模型幻覺」這個風險自動消失。**

多模態模型讀不清楚時，傾向**編一個看起來合理的日期**而不是承認讀不到。
在硬擋 FIFO 的場景這是最危險的失敗模式——編出來的日期可能剛好通過檢核，
系統於是「安靜地放行一筆違規領用」：不報錯、log 乾淨、稽核看不出來。

但在封閉候選集下，編出來的日期幾乎不可能命中清單裡的某一批，**對不上就當場暴露**。
原本需要靠「同張圖跑兩次比對」這種笨方法防的事，變成系統的天然性質。

**而且反過來還能容錯。** 讀成 `2026-08-l2`（1 誤認成 l）這種，
只要候選清單裡只有一個接近值，就能安全判定。
開放式辨識不敢做的模糊比對，封閉候選集下反而可以做。

## 3. 元件責任

| 元件 | 責任 | 為什麼這樣切 |
|------|------|-------------|
| `CaptureSource`（前端介面） | 影像來源抽象：瀏覽器相機（含 USB 工業相機，換 deviceId 即可）/ 檔案上傳 / 未來遠端相機 | 把「影像從哪來」與「影像怎麼處理」切開。擷取層只吃 Blob，換相機不動流程。後端 `CameraGateway` 本期只留抽象（~15 行）不寫實作 |
| 影像擷取層（前端） | 自動抓取（畫面穩定即快門）→ 連拍 3-5 張擇最清晰 → **人確認** | 純瀏覽器、零依賴起步、**不依賴 Gemini**，可與流程開發併行。連拍擇優是辨識鏈裡投報率最高的一招：手持十張常糊三張，自動挑掉比調 prompt 有效且免費 |
| `recognition_service` | 影像 → JSON。**無狀態**，不碰 session、不碰 model | 唯一會因供應商/模型迭代而頻繁改的地方，隔離開來。介面不綁 Gemini SDK 型別 → 換供應商只換實作 |
| 正規化對映 | 型號簡寫、4 種日期格式 → 標準值。**純函式** | 人工輸入版就要用，先寫先測；辨識上場直接複用，不重寫 |
| `fifo_service` | 候選集比對 + FIFO 判定 | 產品價值所在。與辨識準確率**解耦**，可各自迭代 |
| `lot_service` | 收貨建批 / 扣庫存，`SELECT FOR UPDATE` 鎖 lot | 四台機台可能同時領同一料號，不鎖會扣成負數 |
| `post_material_usage` | 本期**空殼**，只寫 `audit_log` | 會計引擎 Phase 6 才做。介面先留，屆時只換實作，領用流程不動 |
| `inventory_items` | 包材（Phase 7 起含成品）品項主檔。**新表，不放既有 `products`** | `products.product_code` 只有 String(20)，料號 `2003.T7320BC-340X900-P1` 有 23 字元塞不下；其 22 欄有 11 欄是軟體銷售專用（授權/計費/收入認列/底價）；且 `products` 是 Phase 9 要清的 CRM 表——新地基不蓋在要拆的牆上 |
| `inventory_lot` | 批次 + `receipt_date`（★ FIFO 排序鍵） | 全案唯一地基改動。**批次資料的 SoT 只能有一份**——這也是本模組不獨立成系統的理由 |
| `material_usage_scan` + `material_usage_line` | 領用一箱一筆（扣庫存在此層）＋ 使用明細一對多 | 表單實證：一箱膜可包多產品、跨多機台，各有步徑。單一欄位塞不下，硬塞成 `"休D/金尊"` 字串則 US-5 追溯查不動 |

## 4. 三個刻意的設計約束

**① 辨識可斷，系統不可斷。**
API 逾時、網路斷線、辨識失敗 → 一律退回人工輸入（US-3 本來就要做），
**仍須通過 FIFO 檢核**。所以人工輸入版不是「陽春版」，是常駐的退路。
這也是實作順序先做它的原因。

**② 錯誤不可以是安靜的。**
辨識服務掛掉時，系統會安靜退回人工，現場只會覺得「今天系統比較笨」而**不會有人報修**，
可能壞好幾天沒人知道。→ 辨識失敗率超過門檻必須**主動告警**。
異常看板的「沒有錯誤」也要主動顯示且帶時間戳——
一片空白分不出「一切正常」和「壞掉沒回報」。

**③ 扣庫存與寫紀錄必須同一個 transaction。**
中途失敗要一起 rollback。這條規矩之後接會計分錄時同樣適用。

**④ 自動化「對準與快門」，但不自動化「判斷」。**
自動抓取省掉的是戴手套時對焦按鈕的手忙腳亂；
確認畫面（顯示鎖定到哪一批）保留，因為那是「這不是我拿的那箱」的最後一道防線。
何況作業員本來就要選產品/機台/步徑，一定會碰平板——省掉快門的邊際效益有限，
省掉確認的代價卻很大。

> ⛔ **部署前提**：`getUserMedia` 需要 secure context。現場平板若以 `http://192.168.x.x`
> 連內網伺服器，瀏覽器**直接擋掉相機**（給權限也沒用）。內網 HTTPS / 內部網域憑證 /
> Cloudflare Tunnel 三選一，**必須在上線前解決**。
