> **狀態**: Draft v1.2 — 2026-08-21（v1.2：Q11 亦 no，兩條退路皆關，辨識 PoC 成為唯一路徑）

> **本版變更**: 從 ERP 模組**抽出成獨立產品**。四項定位變更（見 §1.3）：

## 1. Goal — Who / What / Why

### 1.1 一句話

**把「哪一批包材、什麼時候、被誰、用在哪個產品上」變成查得到、追得到、稽核得了的紀錄**，
不需要買一整套 ERP。領用時拍箱子取代抄表單，FIFO 檢核與到期提醒疊在紀錄之上。

### 1.2 Who

| 角色 | 在系統裡做什麼 | 使用裝置 |
|------|--------------|---------|
| **包裝線作業員** | 領用時拍照 + 選填四欄；事後補使用明細 | 現場平板 |
| **倉管** | 收貨建批（登進貨日/數量）；處理辨識失敗；看到期與呆滯提醒 | 平板 / 桌機 |
| **廠長 / 品管主管** | 覆核非 FIFO 領用；查追溯鏈；看違規報表與異常告警 | 桌機 |
| **系統管理者** | 設定廠別參數：表單欄位、機台清單、選單選項、正規化對映 | 桌機 |

> 相對 M7 少了「會計」角色 —— 獨立產品不做分錄（見 §4 Out of Scope）。
> 多了「系統管理者」—— 因為 Day 1 就是可配置產品。

### 1.3 Why 要獨立成產品（相對 M7 的四項定位變更）

| # | M7（ERP 模組） | Urd-WMS（獨立產品） | 為什麼改 |
|---|---------------|-------------------|---------|
| C1 | 批次庫存靠 ERP 的 M2 入庫建立 | **自持批次 SoT，自帶收貨建批** | 沒有 ERP 也要能跑。代價見 R5 |
| C2 | 欄位寫死金軒揚表單 P-4-P-01-07 | **設定驅動**：欄位、選單、機台、對映表皆可配置 | 要能複製給第二家工廠 |
| C3 | 只有 FIFO 即時擋單 | **四類提醒**：FIFO 擋單、效期/呆滯、待補明細、稽核異常 | 紙本時代看不到的東西，數位化後才有能力主動講 |
| C4 | 落帳走 ERP `posting_service` | **不落帳**，只留領用事件紀錄 | 輕量化。會計是 ERP 的事 |

### 1.4 Why now — 真實痛點（M7 已驗證，不重複舉證）

1. **FIFO 失控無人即時發現** — 紙本上已有違規實例（實照 `IMG_2921.jpg` 第 7 列），但要事後翻表才知道。
2. **手抄成本與錯誤** — 作業員要跑去看箱子側面的紅章、抄兩個日期，字跡潦草、格式不一。
3. **追溯鏈斷裂** — 「哪批膜包了哪批成品」只存在紙上；召回時要翻箱倒櫃。
4. **GMP 稽核** — 表單是品質文件體系的一環，數位化後可即時稽核而非年度翻檔。

## 2. ★ 承接自 M7 的三條不可動搖原則

這三條是 M7 已拍板、Urd-WMS 全盤繼承的設計憲法。任何實作決策與之衝突時，以此為準。

### 2.1 紀錄 > 擋單

交付的核心是**紀錄**，不是攔截。擋單是加值，但它服務於紀錄，不能反過來威脅紀錄。

- **被擋 ≠ 沒發生**：`blocked_fifo` 是一筆完整紀錄（誰／何時／哪台機／拿了哪批／應該拿哪批／當時影像），永久保存、不可刪。
- **畫面語氣**：紅屏不是「失敗，請重試」，是「**已記錄，請換一箱**」。前者誘發「再拍一次讓它過」。
- **取捨時選記**：擋失敗只漏一次違規；沒紀錄是核心價值破洞。
- **測試優先序**：最高優先不是「違規被擋」，是「任何情況下都留得下紀錄」——斷網、拍到一半離開、重複拍、系統當掉重開、覆核駁回。

### 2.2 辨識是「認出是哪一批」，不是「讀出一個日期」

進貨日**不是從照片來的**，是收貨時由倉管登錄進 `inventory_lot`（US-1）。
領用時的辨識任務是：從一份**已經存在而且很小**的候選清單裡挑一個。

```
辨識讀出日期 → 比對「該料號 qty_on_hand > 0 的批次清單」（通常 1-5 批）
  ├─ 命中唯一 → 鎖定批次 → 跑 FIFO 判定
  ├─ 對不上任何一批 → 辨識錯 or 此箱未入帳 → 退人工（US-4）
  └─ 命中多個 → 退人工確認
```

**這讓模型幻覺這個風險自動消失。** 多模態模型讀不清楚時傾向編一個合理日期而非承認讀不到；
編出來的日期若剛好通過檢核，系統會**安靜放行一筆違規**——不報錯、log 乾淨、稽核看不出來。
封閉候選集下，編出來的值幾乎不可能命中清單裡某一批，**對不上就當場暴露**。

反過來還能容錯：讀成 `2026-08-l2`（1 誤認成 l），只要候選清單裡只有一個接近值就能安全判定。

### 2.3 辨識可斷，系統不可斷

API 逾時、網路斷線、辨識失敗 → 一律退回人工輸入（US-4），**仍須通過 FIFO 檢核**。
人工輸入版不是陽春版，是常駐退路，也是實作順序上最先做的東西。

## 3. User Stories

優先序：**P0** = v1 上線必備 ／ **P1** = v1 應有 ／ **P2** = v1.1 可延後。

### US-1: 收貨建批（獨立產品的新地基）
**P0**

**As a** 倉管
**I want to** 收貨驗收時登錄「這一批的料號、進貨日、數量」
**So that** 領用端有 FIFO 比對的基準，而不必依賴外部 ERP

**Acceptance Criteria:**
- [ ] Given 一批到貨包材，when 倉管輸入料號 + 進貨日 + 箱數（+ 選填製造日 / 原廠 ROLL#），then 建立 `inventory_lot` 並設 `qty_on_hand = 箱數`
- [ ] Given 同料號同進貨日已存在批次，when 再次收貨，then 提示「要併入既有批次還是另開一批」，由倉管決定（不自動併）
- [ ] Given 進貨日填成未來日期，when 送出，then 擋下並提示（打錯字的常見情形）
- [ ] Given 收貨紀錄已建立，when 事後發現數量登錯，then 可修正但寫入 audit_log（不可靜默改）
- [ ] **期初庫存**：Given 系統首次上線，when 倉管用同一介面補登現有在庫箱子，then 建立起始批次（不另做匯入工具）

> 📌 這是 M7 沒有的入口。M7 靠 ERP 的 M2 入庫；獨立後必須自己有，否則整套跑不起來。

---

### US-2: 拍照領用登錄
**P0**

**As a** 包裝線作業員
**I want to** 拍一張箱子就帶出型號 / 製造日 / 進貨日
**So that** 不用跑去看側面的章再手抄

**Acceptance Criteria:**
- [ ] Given 平板相機對準箱子，when 畫面穩定，then 自動連拍 3–5 張擇最清晰者（不需按快門）
- [ ] Given 拍到影像，when 辨識完成，then 回填型號 / 製造日 / 進貨日三欄，且**顯示鎖定到哪一批**供人確認
- [ ] Given 辨識結果錯誤，when 作業員就地更正，then 以更正值重跑候選集比對
- [ ] Given 三欄已確認，when 作業員選填設定檔定義的人工欄位（預設：上膜/下膜、包裝產品、包裝機台、使用步徑），then 可送出
- [ ] Given 送出成功，then 原始影像**永久留存**且可從紀錄點開（稽核唯一證據）
- [ ] Given 通過 FIFO 檢核，then `status = posted`，`inventory_lot.qty_on_hand -= 1`
- [ ] **扣庫存與寫紀錄必須在同一個 DB transaction**，中途失敗一起 rollback
- [ ] Given 四台機台同時領同一料號，when 併發送出，then 用 `SELECT FOR UPDATE` 鎖 lot，不得扣成負數
- [ ] Given 網路中斷，when 作業員送出，then 影像與表單暫存本機，恢復後自動補送並保留原始 `captured_at`

> 顆粒度已定（M7 2026-08-21 拍板）：**一箱＝一捲，每次領一箱**。`qty_on_hand` 單位＝箱，領用減 1。
> 出了倉庫就當用完，**不做退回、不做部分扣量**。

---

### US-3: 非 FIFO 當場擋下並說清楚該拿哪箱
**P0**

**As a** 包裝線作業員
**I want to** 拿錯批次的當下就知道
**So that** 還來得及換一箱，而不是月底被稽核翻出來

**Acceptance Criteria:**
- [ ] Given 已鎖定批次，when 系統查該料號 `qty_on_hand > 0` 的最早 `manufacture_date`，then 掃到的 `manufacture_date` 較晚 → 判違規
- [ ] Given 判違規，then `status = blocked_fifo`，**不扣庫存**，但**寫下完整紀錄**（誰/何時/哪台機/拿了哪批/應拿哪批/影像）
- [ ] Given 違規畫面，then 明示「**已記錄，請換一箱**」+「應領用：製造日 YYYY-MM-DD 那批」+ 該批位置/批號
- [ ] Given 同一製造日有多批，then 視為並列合法，任一皆可
- [ ] Given 批次未填 `manufacture_date`，then 排在**最後**（未知年齡不得插隊到已知年齡前面）
- [ ] Given 該料號在庫批次**全部**沒有 `manufacture_date`，then 退回以 `receipt_date` 排序，且畫面明示這是退而求其次
- [ ] Given 違規紀錄已寫入，when 任何人嘗試刪除，then 拒絕；僅可經 US-5 覆核放行或主管作廢（需填原因）
- [ ] Given 同一箱被連續拍第二次想「讓它過」，then 仍判違規並再記一筆（重拍不會讓紀錄消失）

---

### US-4: 辨識失敗的人工補登
**P0**

**As a** 作業員
**I want to** 章糊掉、標籤磨損、或系統辨識不出來時能手動填
**So that** 不會卡住整條包裝線

**Acceptance Criteria:**
- [ ] Given 辨識信心度低於門檻 / 欄位缺漏 / 候選集命中 0 或 >1，then `status = blocked_unreadable` 並轉人工
- [ ] Given 轉人工，when 作業員從**在庫批次清單**中直接挑一批（不要求打字），then 完成鎖定
- [ ] Given 人工鎖定完成，then **仍須通過 US-3 的 FIFO 檢核**（人工不是免檢通道）
- [ ] Given 辨識服務完全無回應（逾時/斷線/API 掛掉），then 自動退人工且**不阻塞**，同時記錄失敗原因供 US-9 統計
- [ ] Given 人工補登，then 記錄操作者與時間

> ⚠️ **US-4 可能不只是退路。** Q1 答 no（章改不掉）之後，若 PoC 顯示候選集命中率不足，
> 這裡的「從在庫批次清單挑一批」會變成日常主要操作路徑。
> → **挑批 UI 要當主力畫面設計**（大按鈕、批次資訊一眼可辨、預設排在最早製造日），
>   不能做成陽春的錯誤處理畫面。見 §6 R1。

---

### US-5: 合法非 FIFO 的覆核放行
**P0**

**As a** 廠長／品管主管
**I want to** 對正當例外放行
**So that** 現場不會為了趕產線而學會繞過系統

**Acceptance Criteria:**
- [ ] Given `status = blocked_fifo` 的紀錄，when 具權限者放行，then **必須填選原因**（試產指定批 / 舊批破損不可用 / 規格臨時變更 / 急單 / 其他+說明）
- [ ] Given 放行完成，then `status = overridden`，扣庫存，覆核者/時間/原因寫入 audit_log
- [ ] Given 一般作業員，when 嘗試放行，then 拒絕（無此權限）
- [ ] Given 放行被駁回，then 紀錄保留為 `blocked_fifo` 並記下駁回者與理由

> ⚠️ **US-5 是硬擋成立的前提，不是加分項。** 硬擋 + 無正當例外出口 = 作業員學會不拍照直接用（見 R2）。

### US-6: 使用明細補齊 + 待補提醒
**P1**

**As a** 作業員 / 線長
**I want to** 領走時先不填「這箱包了哪些產品、各多少步徑」，事後再補
**So that** 領用當下不必知道未來的事，但追溯鏈最終還是完整的

**Acceptance Criteria:**
- [ ] Given 一箱膜可包多產品、跨多機台，then 使用明細是**一對多**（scan 一筆 → line 多筆），不塞成 `"休D/金尊"` 字串
- [ ] Given 領走當下不知會包哪些產品，when 送出，then 允許 `status = posted` 但標記「明細待補」（庫存已扣）
- [ ] Given 明細待補超過設定時數（預設 24h），then 推播提醒該筆的登記人與線長
- [ ] Given 待補筆數超過設定門檻，then 升級通知主管
- [ ] Given 任一看板，then **顯示未補齊筆數**且帶時間戳（不能只在有問題時才顯示，見 §2.1 測試優先序）

---

### US-7: 追溯查詢（GMP 召回用）
**P0**

**As a** 品管
**I want to** 從包材批次查到所有用它包過的成品，反向也要能查
**So that** 召回時不必翻紙本

**Acceptance Criteria:**
- [ ] **正向**：Given 包材批次（料號＋進貨日＋製造日），then 列出所有領用紀錄與包裝產品、機台、步徑、時間、人
- [ ] **反向**：Given 成品名稱 + 期間，then 列出用過的所有包材批次
- [ ] Given 任一筆結果，when 點擊，then drill-down 到原始影像
- [ ] Given 查詢結果，when 匯出，then 產出**等同紙本表單格式**的稽核報表（欄位由設定檔決定，見 US-11）
- [ ] Given 被擋下的違規紀錄，then **也出現在追溯結果中**並標明狀態（因為實體可能真的被用了，見 R3）

---

### US-8: 效期 / 呆滯 / 低水位提醒
**P1**

**As a** 倉管
**I want to** 系統主動告訴我哪批快過期、哪批壓倉底太久、哪個料號快沒了
**So that** 不用每週自己去翻庫存表

**Acceptance Criteria:**
- [ ] Given 批次的 `manufacture_date` + 該料號設定的保存期限，when 剩餘天數低於門檻，then 推播「效期將屆」提醒（含批次、剩餘天數、在庫箱數）
- [ ] Given 批次 `receipt_date` 距今超過門檻天數且 `qty_on_hand > 0`，then 推播「呆滯批次」提醒
- [ ] Given 某料號在庫總箱數低於設定安全水位，then 推播「低水位」提醒給倉管
- [ ] Given 門檻值，then 皆為**每料號可覆寫**的設定（不同膜保存期限不同）
- [ ] Given 未設保存期限的料號，then 不發效期提醒且**不當作錯誤**（呆滯與低水位仍照發）
- [ ] Given 提醒已發出且情況未解除，then 不重複轟炸（同一批次同一類提醒有冷卻期）

> 📌 全新需求，M7 沒有。這是「有了批次資料之後才做得到」的加值，也是 `manufacture_date` 從備用欄位變成有用欄位的地方。

### US-9: 稽核異常告警（系統壞掉要有人知道）
**P1**

**As a** 廠長 / 系統管理者
**I want to** 辨識準確率掉下去、違規累積沒人覆核時主動被通知
**So that** 系統壞掉不會安靜地壞好幾天

**Acceptance Criteria:**
- [ ] Given 滾動視窗內辨識失敗率超過門檻，then **主動告警**（不是等人去看報表）
- [ ] Given `blocked_fifo` 未覆核筆數超過門檻或停留超過設定時數，then 告警給主管
- [ ] Given 辨識服務連續 N 次無回應，then 告警給系統管理者
- [ ] Given 異常看板一切正常，then **仍主動顯示「正常」並帶最後檢查時間戳**——一片空白分不出「一切正常」和「壞掉沒回報」
- [ ] Given 告警管道（Email / Telegram / 站內），then 可設定

> 📌 出自 M7 架構的設計約束②「錯誤不可以是安靜的」，M7 只寫在架構沒寫成需求，此處補上。

### US-10: FIFO 違規追蹤報表
**P1**

**As a** 廠長
**I want to** 看違規次數、原因分布、常違規的品項與班別
**So that** 知道是人的問題、儲位的問題，還是流程的問題

**Acceptance Criteria:**
- [ ] Given 期間，then 列出 `blocked_fifo` + `overridden` 筆數與占總領用比率
- [ ] Given 結果，then 可依 override 原因 / 料號 / 機台 / 班別分組排名
- [ ] Given 任一列，when drill-down，then 看到單筆紀錄與影像

### US-11: 廠別配置（可複製給第二家工廠的關鍵）
**P0**

**As a** 系統管理者
**I want to** 用設定檔定義表單長什麼樣、有哪些機台、料號怎麼正規化
**So that** 換一家工廠不需要改程式

**Acceptance Criteria:**
- [ ] **人工欄位**可配置：欄位名稱、型別（單選 / 多選 / 數字 / 文字）、選項清單、是否必填
      （金軒揚預設：上膜/下膜、包裝產品、包裝機台、使用步徑）
- [ ] **機台清單**可配置（金軒揚預設：D-003 / D-004 / D-023 / D-027）
- [ ] **正規化對映表**可配置：

## 5. 資料模型骨架（供 eng-review 細化）

```
factory_config      ── 廠別設定：欄位定義、機台清單、對映表、提醒門檻、報表格式
inventory_item      ── 包材品項主檔（料號可達 23+ 字元；不共用任何 CRM/產品表）
  └─ inventory_lot  ── 批次：manufacture_date ★FIFO 排序鍵 / receipt_date（同製造日
                       時的次鍵、呆滯天數基準） /
                       supplier_lot_code / qty_on_hand / warehouse_id
       └─ material_usage_scan   ── 領用一箱一筆：captured_at / captured_by / image_url /
                                   ocr_raw / confidence / status / fifo_expected_lot_id /
                                   override_by / override_reason / field_values(JSON)
            └─ material_usage_line ── 使用明細（一對多）：包裝產品 / 機台 / 步徑
alert_rule / alert_event  ── 提醒規則與已發事件（冷卻期用）
audit_log           ── 覆核、作廢、設定變更、數量修正
```

`status` 狀態機：
```
pending ──辨識成功&FIFO過──> posted
   │                          └─(明細待補)─> posted + pending_detail
   ├──辨識不出──> blocked_unreadable ──人工鎖定──> (回 FIFO 檢核)
   └──FIFO違規──> blocked_fifo ──覆核放行──> overridden ──> (扣庫存)
                       └──主管作廢(需原因)──> voided
```

> 所有 `blocked_*` 與 `voided` 皆為**完整紀錄**，永久保存、不可刪。

## 6. Risks

**R1 — 進貨日是手蓋橡皮章，而且改不掉。（2026-08-21 升級：退路已關閉）**
紅色橡皮章：歪斜、墨色深淺不一、蓋在瓦楞紙上、可能蓋歪出框。
印刷標籤 OCR 是成熟問題，**手蓋章不是**。

> 📌 **D2 改判後，這條風險的分母變了。** FIFO 排序鍵已改成 `manufacture_date`（見 §7），
> 橡皮章不再是排序鍵的唯一來源。**但還不能宣告 R1 降級** —— 要先確認一件事：
> **製造日在箱上是印的還是蓋的？** 若是原廠印刷 → R1 實質大幅降低（OCR 回到成熟問題）；
> 若也是手蓋 → R1 原封不動。PoC 取樣時要分開統計這兩欄的辨識表現，不要合併成一個準確率。

**兩條退路都關了（Peter 2026-08-21 拍板）**：
- Q1 「改貼列印標籤取代橡皮章」→ 不可行
- Q11「章照蓋、另外加貼一張系統印的 QR」→ **現在不行**（原話：「未來可能可以，但不是現在」）

所以 v1 沒有「換一個好辨識的載體」這條路，只能在既有的手蓋章上把辨識做起來。

> 📌 **Q11 是 v2 最大的槓桿，不是死題。** 「現在不行」多半是流程與現場配合的時機問題，不是技術問題。
> → 影響 v1 的設計：批次的**識別方式要留一層抽象**（今天是「辨識影像 → 比對候選集」，
>   未來可能是「掃 QR → 直接命中」）。不要把「一定要經過影像辨識」寫死進領用流程，
>   否則 v2 要加掃碼時得動主流程。這層抽象成本很低，現在留、以後省。

→ **唯一的防線是 §2.2 的封閉候選集。** 這條設計因此從「加分」升格為「本案能不能成立的關鍵」。
   它的成立條件是：**同一料號在庫批次數少（1–5 批）且進貨日彼此拉得開**。
   若某料號同時在庫 8 批、進貨日只差幾天，容錯空間會被吃光 → 退人工比例飆高。
→ **PoC 要量的不是 OCR 準確率，是候選集命中率。** 這是兩個不同的指標：
   讀成 `2026-08-l2` 但候選集裡只有一個接近值 → **算命中**（OCR 錯了但系統對了）。
   驗收門檻應該訂在「命中率」與「誤命中率」，不是「字元正確率」。
   ⚠️ **誤命中（挑到錯的一批但系統以為對）是本案最嚴重的失敗模式** —— 它會安靜放行一筆違規。
   PoC 必須分開報這兩個數字，不能只報一個總準確率。
→ **若命中率不足**：US-4（人工從在庫批次清單挑一批）會從退路變成主要操作路徑。
   這不是災難——紀錄仍然完整、FIFO 仍然檢核（§2.1 紀錄 > 擋單），只是「拍照省事」的賣點縮水。
   設計時 US-4 的挑批 UI 必須做到能當日常主力用，不能做成陽春的錯誤處理畫面。

**R2 — 沒有 override 通道，現場必然繞過系統。**
硬擋 + 無正當例外出口 = 作業員學會不拍照直接用。比軟擋更糟：資料全綠，實際失控。
→ US-5 是前提不是加分項。

**R3 — 「硬擋」擋不住物理領用。**
系統只能擋帳與警示，擋不住人把膜裝上機台。
→ 必須接受「已用但未落帳」的中間狀態；`blocked_*` 紀錄要出現在追溯結果（US-7）。

**R4 — 相機需要 secure context（部署硬前提）。**
`getUserMedia` 在 `http://192.168.x.x` 下**被瀏覽器直接擋掉**，給權限也沒用。
→ 內網 HTTPS / 內部網域憑證 / Cloudflare Tunnel 三選一，**必須在上線前解決**。

**R5 — 獨立產品的代價：批次 SoT 分家。**
本產品自持 `inventory_lot`。若同一家工廠日後也導入 Norns-ERP，兩邊各有一份批次庫存，
會需要對帳或單向同步。**v1 明確不做**（你已拍板），但要知道這筆帳存在。

📌 **Norns-ERP 的 M7 處置（2026-08-21 拍板）：各走各的。** 那邊已落地的 backend
（`services/packaging/`、`models/inventory.py`、alembic `a6eeb88851d8`）保留不動、繼續當 ERP 模組演進。
兩邊自此是**平行的兩份實作**，不做程式碼共用、不同步 schema。
→ 代價：同一個 domain 的 bug 要修兩次，設計改動不會自動傳播。
→ 這是刻意接受的，因為兩者目標客戶不同（買整套 ERP vs 只買這一塊）。
→ 但 M7 的三條原則（§2）是共同祖先，兩邊都不該偏離；偏離時以本文件為 Urd-WMS 的準。
→ 緩解：領用事件表結構設計時保持「可被外部系統消費」（欄位齊全、有穩定 ID），
   即使本期沒有推送介面，未來補一支匯出/webhook 的成本仍低。

**R6 — 「輕量」與「Day 1 可配置」互相拉扯。**
可配置會誘發過度抽象（M7 架構的紀律是「第二實例才驗證抽象」）。
→ 本 requirement 的處理：**資料模型可配置、功能範圍窄**。
   可配置的只有 US-11 列的五類（欄位/機台/對映/門檻/報表），其餘一律寫死。
   任何「順便也做成可設定」的提議，要先問「第二家工廠真的會不一樣嗎」。

## 7. 決策異動（相對於繼承的 M7 決策）

Urd-WMS 從 Norns-ERP M7 抽出後**各走各的**（Peter 2026-08-21），以下記錄兩邊已經分岔的決策。
`docs/_inherited/` 是 M7 當時的快照，**不回頭改**，看差異看這張表。

| 編號 | 決策 | M7 原判 | Urd-WMS 現判 | 改判理由 |
|------|------|---------|--------------|----------|
| D2 | FIFO 排序基準 | **進貨日 (receipt_date)** | **製造日 (manufacture_date)**，同日時以進貨日為次鍵 | Peter 2026-08-21：「一律看製造日期判斷出貨」。進貨日只說明「什麼時候到我們手上」，供應商壓貨或延遲交貨就會把順序打亂 —— 三月製、八月才到的膜，實際上比七月製、六月就到的更舊。要控管的是**庫齡**，不是到貨順序 |

**連帶影響**（已一併改掉，不是待辦）：
- 未填製造日的批次排**最後**，不是最前。未知年齡插隊到已知年齡前面，等於用「沒資料」換到優先權
- 整個料號都沒有製造日 → 退回進貨日排序，且 API 回 `fifo_basis` 讓畫面說清楚這是退而求其次
- 呆滯提醒（US-6）**仍看 `receipt_date`** —— 那問的是「壓在我們倉庫多久」，本來就該用到貨日
- 效期提醒（US-6）**仍看 `manufacture_date` + 保存期限**，不受影響
